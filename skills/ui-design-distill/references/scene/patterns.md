# Task and component patterns

Start from objects, actors and jobs: what is managed, which person can act, how
often, and what success means. Record data magnitude/ranges and the significance
of zero, missing, loading and error values. Styling cannot repair contradictory data.

A component pattern records purpose, anatomy, variants actually used, state
coverage, responsive/platform behavior, keyboard/labeling requirements and known
consumers. Similar visuals with different semantics stay separate. Use available
native or tested primitives; brand expression should not replace expected behavior.

A task pattern names actor, goal, entry/success states, actual path and recovery.
A transition has a pre-state, action, post-state and observed trace. Keep roles,
permissions and data conditions where they alter the path. Do not collapse the
product into a set of screenshots or enforce an identical state list on every
control. Mark not-applicable separately from not-inspected.

Use source design taste as evidence for density, emphasis, color roles and motion
purpose. Shared information hierarchy does not require a universal sidebar color,
font size, no-chart rule or animation duration. High-frequency UI may favor quiet
feedback while a rare milestone may support stronger expression; record context.

Prioritize recorded task needs over introducing a signature motif. Source defects
or missing recovery states become identified gaps; source fidelity is not a reason
to reproduce broken behavior. User-requested improvements are explicit extensions.
